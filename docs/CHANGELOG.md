## 0. 版本口径（先分清两种「版本」）

| 口径 | 当前值 | 由谁决定 | 何时升 |
|---|---|---|---|
| **应用版本** `package.json.version` | **1.4.0** | 用户可见的能力 / 表现变化 | 有可交付的能力变化即升 |
| **Scene Schema 版本** `SCHEMA_VERSION` | **1.3.0** | `SceneDocument` 的**顶层结构与迁移语义** | 只在存档结构或迁移规则变化时升 |
| 视觉体系版本 | v1.0（制图语言） | UI 设计规范 | 独立演进，[VISUAL_STYLE.md](VISUAL_STYLE.md) |
| 美术设定版本 | v1.1（三渲二日常） | 三维场景表现规范 | 独立演进，[ART_DIRECTION.md](ART_DIRECTION.md) |

**为什么 v1.4.0 没有把 Schema 升到 1.4.0**：本轮新增的是 `rules.pipeline.landUse.mixMode` / `mix` 两个规则键，以及渲染层与预设层；`SceneDocument` 的顶层字段（`rules / graph / parcelEdits / regions / overrides`）一个没变。`schema.ts` 已有「缺字段即补默认」的无条件迁移，v1.3.0 存档可以无损加载并生成相同结果（`preset.test.ts` 与 `landUseMix.test.ts` 覆盖）。升 Schema 会让所有 v1.3.0 存档落入 legacy 分支，增加风险且没有收益。**应用版本与 Schema 版本刻意不同步，是设计决定，不是遗漏。**

**一致性规则**（由 `src/__tests__/version.test.ts` 自动检查）：
1. `package.json` 与 `package-lock.json` 的 `version` 必须一致；
2. README「版本演进」与本文必须包含当前应用版本号；
3. `SCHEMA_VERSION` 与 `MIGRATABLE_VERSIONS` 必须与本文记录一致。

### 史料说明（避免用 git log 反推项目历史）

**这个项目从 V0.1 起就是用户与 Hy4 在同一套架构判断上持续协作做出来的，中间换过设备、换过会话；不是后来接手的陌生仓库。** Git 是在 [DEVELOPMENT_STORY.md](DEVELOPMENT_STORY.md) 阶段五「新建仓库，保留旧库」时才初始化的，因此仓库第一个提交就是 v1.2.0 完整版、总提交数远少于真实迭代轮次。**git log 只记录交付后的版本管理，不能用来推断迭代史**；V0.1 / v1.1.0 的史料在 `DEVELOPMENT_STORY.md` 与 `docs/screenshots/` 的历史存档截图里。

跨设备 / 跨会话能接得上，靠的不是聊天记录，而是三样东西：**可复现的测试基线**（每次接续先 `npm test` 与指纹核对，不靠记忆推断）、**逐阶段的开发过程记录**、以及**本文这份版本演进**。这也是为什么 v1.4.0 要把版本口径、指纹基线、架构判断与「明确未做」都落成文档 —— 它们是给下一次接续的锚点。

### 2.2 六个影响架构的判断

1. **先审规则再加功能。** 用户观察到「广场和绿地压在道路上面」，上机实测确认不是渲染错觉而是几何重叠，且当时空间校验 **PASS** —— 根因是退界逻辑散落在建筑 / 树 / 公园三个阶段，校验器缺「公园 vs 道路」这一对。修法是收成单一关系矩阵，而不是给公园打补丁。
2. **共享构件库 + 按功能装配，不逐栋精模。** 400 m 165 栋、800 m 752 栋，逐栋建模不可维护。13 个共享 box 原型 + 实例色，只增加 1 个 draw call；差异只允许出现在 L4 装饰层，L2 窗格全城同模数。
3. **场景主题与 UI 主题彻底解耦。** `SheetTheme` 只管面板配色，`SceneTheme` 独立管视口，切换不写 `SceneDocument`、不影响指纹。修复 UI 双主题时还发现了早期「配色回退」把两套变量写成逐行相同的历史债。
4. **默认预设必须连道路图一起内置。** 只抄 9 个规则参数会生成 285 节点规则网格（727 栋 / `D06F6737`），而用户存档是 400 m 网格缩放后的 77 节点持久化图（752 栋 / `DCA491B5`）——是两座城。
5. **400 m 保留为工程测试基准。** 203 个用例以它为基准，改成 800 m 会让大量断言失效、整套测试耗时从 ~1.5 分钟涨到 5 分钟以上。用户首屏走 `createPresetDocument()`，测试走 `createDefaultDocument()`，两者明确区分并有测试锁定。
6. **2 km 判定为非目标，LOD / 分块不投入。** 目标范围 800–1200 m（字段上限本来就是 1200，UI 调不到 2000 m）；生成侧分块会连带重写 `sample()` 稳定序号语义、校验分区与确定性契约，4–8 周成本在目标范围内无对应收益。`tiles.ts` 保留为评估证据，不接生产路径。决断见 [ROADMAP_v1.3.md §3.1](ROADMAP_v1.3.md)。

### 2.3 兼容性与迁移

| 项 | 处理 |
|---|---|
| v1.0.0 / v1.1.0 / v1.2.0 存档 | `MIGRATABLE_VERSIONS` 自动迁移（补 `pipeline` 分组、可编辑图） |
| v1.3.0 存档 | `version === SCHEMA_VERSION` 分支；缺 `landUse.mixMode` / `mix`、`extensions.*`、`mobility.*` 时**只补缺失键**，非法值交给 `RULE_FIELDS` 校验拒绝，不在迁移里洗白脏数据 |
| `mix` 键空间 | 白名单只到 group 层，额外补一层校验：只允许 4 个已注册功能项且为非负数值 |
| `SceneDocument` 顶层结构 | **未变**，因此 Schema 保持 1.3.0 |
| 默认场景 | 首屏 / 「重置」/`scene.reset` / 不带尺寸的 `scene.create` → 800 m 预设；`createDefaultDocument()` → 400 m 工程基准 |
| 曾保存过旧场景 | `initialDoc()` 仍优先加载 localStorage 存档，不擅自清用户数据；点一次「重置」切到新默认 |

### 2.4 明确未做（不写成已做）

- 生成侧按瓦片分块、渲染循环接入视锥裁剪、LOD —— **判定不做**（§2.2 第 6 条）
- 自由节点拖拽编辑、Inspector 区域可视化编辑、E1 临路退界、E2 高程回填到建筑 / 道路 Y 坐标
- 屏幕空间恒宽 1.5 px 轮廓、共享 atlas / 模块化 UV、生活物件密度预算与留白控制、功能盲测、2 km 帧率
- `transit` / `leisure` 正式入 Schema（当前走设施实例层）
- LLM 代理带真实密钥的端到端联调（需 `OPENAI_API_KEY`）
- 更贴合规划生产口径的下一步：**GeoJSON / DXF 红线导入 + 按红线分区**（1–2 周量级），尚未启动

## 3. 历史版本摘要

- **V0.1 · 确定性优先**：单函数生成 + `sample(seed, 属性盐, 稳定序号)`，放弃全局 RNG 流，解决「改东侧不动西侧」；命令白名单把 LLM 关进笼子。39 用例。
- **v1.1.0 · 阶段 DAG**：把扁平流程重构为显式 10 阶段依赖图、拓扑排序、`ctx.upstream()` 运行时守卫。77 用例。
- **v1.2.0 · 可编辑几何**：道路图节点 / 路段可增删改向；地块支持非矩形、凸凹多边形的生成 / 拆分 / 合并 / 顶点编辑；编辑后建筑、公园、树木自动重适配。93 用例。
- **v1.3.0 · 六项后续建议**：区域选择器与规则叠加层（空层是恒等元、不进指纹）、E1 水系 / E2 地形从占位换成实现、多边形布尔升级、可插拔阶段注册表 + 节点图导出、瓦片索引与 2 km 实测、LLM 后端代理。137 用例。完成度与未完成部分见 [ROADMAP_v1.3.md](ROADMAP_v1.3.md)。
- **视觉体系 v1.0（独立线）**：UI 从深色仪表盘改为建筑制图语法（编号 / 引线注记 / 图例 / 比例尺 / 细线直角 / 图案填充），浅色图纸 + 深色海图双主题；v1.4.0 第 6 轮修复了双主题被「配色回退」写成同一份色板的历史债。
